
# Mastering the Build: A Deep Dive into Apache Maven

For Java developers, **Apache Maven** is often the invisible engine room of the project. While it’s ubiquitous, it is frequently misunderstood or used merely as a “library downloader.” However, Maven is a comprehensive project management and comprehension tool based on the concept of a **Project Object Model (POM)**.

In this post, we will dissect Maven’s architecture, explore the build lifecycle, and clarify how it manages the complexities of modern software dependencies.

### The Philosophy: Convention Over Configuration

Unlike its predecessor Ant, which required explicit instructions for every step (compile _this_ directory, put classes _there_), Maven relies on **Convention over Configuration**. It assumes reasonable defaults:

- Source code lives in `src/main/java`
- Tests live in `src/test/java`
- Resources live in `src/main/resources`
- Test resources live in `src/test/resources`
- Output goes to `target/`

If you follow these conventions, your build script (the `pom.xml`) can remain shockingly small. You only need to configure the _exceptions_.

## The Heart of Maven: The POM

The `pom.xml` (Project Object Model) is the blueprint for your Maven project. While it can grow quite large, the vast majority of your work will focus on a specific set of core tags. It contains information about the project and configuration details used by Maven to build the project.

Key elements of the POM include:

### The Root & Identity (The GAV: **Group-Artifact-Version**)

These tags define _what_ your project is and _where_ it sits in the Maven ecosystem. They are mandatory.

- `**<project>**`: The root element of the file. All other configurations reside inside this tag.
- `**<modelVersion>**`: Specifies the version of the POM model (currently always `4.0.0`).
- `**<groupId>**`: The unique identifier of the organization or group that created the project. It usually follows the reverse domain name convention (e.g., `com.citi.markets`, `org.apache.maven`).
- `**<artifactId>**`: The unique base name of the primary artifact being generated by this project (e.g., `trade-processor`, `reporting-service`).
- `**<version>**`: The specific version of the artifact generated by the project (e.g., `1.0.0`, `2.5.0-SNAPSHOT`).
- `**<packaging>**`: Defines the build output format. Defaults to `jar`, but can be set to `war` (web app), `pom` (for parent/aggregator projects), or `ear`.

```
<modelVersion>4.0.0</modelVersion>  
<groupId>com.example.finance</groupId>  
<artifactId>market-data-service</artifactId>  
<version>1.0.0-SNAPSHOT</version>
```

### Dependencies (The Libraries)

This section defines the external JARs your project needs to compile, test, or run.

- `**<dependencies>**`: The wrapper tag for the list of libraries.
- `**<dependency>**`: Represents a single library. Inside this, you must define the `groupId`, `artifactId`, and `version`.
- `**<scope>**`: (Optional) Controls when the dependency is used (e.g., `test` for JUnit, `provided` for Servlet API).
- `**<exclusions>**`: (Optional) Allows you to block specific transitive dependencies that a library might try to pull in unwantedly.

```
<dependencies>  
    <dependency>  
        <groupId>org.springframework.boot</groupId>  
        <artifactId>spring-boot-starter-web</artifactId>  
        <version>3.2.0</version>  
    </dependency>  
</dependencies>
```

### Properties (The Variables)

This section allows you to define placeholders to keep your POM clean and version numbers consistent.  
`**<properties>**`: A key-value map. You can define a version number once here and reference it multiple times using `${property.name}`.

- Common usage: `<java.version>21</java.version>` or `<spring.version>6.1.0</spring.version>`.

```
<properties>  
        <java.version>21</java.version>  
        <junit.version>5.10.0</junit.version>  
</properties>
```

### Build Configuration (The Actions)

This section tells Maven _how_ to build your project, overriding default behaviors.

- `**<build>**`: The container for all build-related configurations.
- `**<finalName>**`: Customizes the name of the generated binary (e.g., `myapp.jar` instead of `myapp-1.0.0.jar`).
- `**<plugins>**`: The list of plugins used during the build.
- `**<plugin>**`: A specific tool execution (e.g., the compiler, the jar packager).
- `**<configuration>**`: Specific settings for that plugin (e.g., setting the Java version for the compiler).
- `**<executions>**`: Defines _when_ (in which lifecycle phase) the plugin should run.

```
<build>  
     <plugins>  
           <plugin>  
                <groupId>org.apache.maven.plugins</groupId>  
                <artifactId>maven-compiler-plugin</artifactId>  
                <configuration>  
                    <source>${java.version}</source>  
                    <target>${java.version}</target>  
                </configuration>  
            </plugin>  
      </plugins>  
  </build>
```

### Inheritance & Aggregation (Multi-Module)

These tags are essential for large enterprise projects where you split code into multiple sub-projects.

- `**<parent>**`: Allows your POM to inherit configuration (dependencies, plugins, properties) from another POM. This is famously used in Spring Boot (`spring-boot-starter-parent`).
- `**<modules>**`: Used in a root POM to list sub-projects. When you build the root, Maven automatically builds all modules listed here.
- `**<dependencyManagement>**`: Defined in a parent POM. It controls the _versions_ of dependencies for child modules, but doesn't actually include the JARs until the child explicitly asks for them (without specifying the version).

==Here is how these tags fit together in a real-world scenario:==

```
<project>  
    <modelVersion>4.0.0</modelVersion>  
      
    <groupId>com.example.finance</groupId>  
    <artifactId>market-data-service</artifactId>  
    <version>1.0.0-SNAPSHOT</version>  
      
    <properties>  
        <java.version>21</java.version>  
        <junit.version>5.10.0</junit.version>  
    </properties>  
  
    <dependencies>  
        <dependency>  
            <groupId>org.junit.jupiter</groupId>  
            <artifactId>junit-jupiter-api</artifactId>  
            <version>${junit.version}</version>  
            <scope>test</scope>  
        </dependency>  
    </dependencies>  
  
    <build>  
        <plugins>  
            <plugin>  
                <groupId>org.apache.maven.plugins</groupId>  
                <artifactId>maven-compiler-plugin</artifactId>  
                <configuration>  
                    <source>${java.version}</source>  
                    <target>${java.version}</target>  
                </configuration>  
            </plugin>  
        </plugins>  
    </build>  
</project>
```

## Maven Basics

Let's understand the basic terminologies and concepts behind Maven first

### Maven Coordinates

**Maven Coordinates** are essentially the unique identifiers for any project, library, or plugin in the Maven ecosystem. Every artifact in Maven has a unique set of coordinates that allows Maven to locate it, download it, and manage it.

These coordinates serve two main purposes:  
1. **Identity:** They define who created the project and what it is.  
2. **Location:** They map directly to a directory path in the Maven repository.

**The “GAV” Trio (Mandatory):** Every single artifact is defined by these three core values.

- `**groupId**` **(Who)**: This represents the organization or group that maintains the project. It follows the Java package naming convention (reversed domain name). _Example:_ `org.springframework.boot`, `com.google.guava`, `org.apache.maven`
- `**artifactId**` **(What)**: This is the specific name of the library or project. It is usually the name of the JAR file without the version. _Example:_ `spring-boot-starter-web`, `guava`, `maven-core`
- `**version**` **(Which one)**: This points to a specific release of the artifact. _Example:_ `3.1.2`, `1.0.0-SNAPSHOT`, `21.0` (most common syntax is major version.minor version.incremental num )

While GAV is always required (in a multi-module project, groupid and version can be inherited from the parent POM), two other coordinates exist for specific use cases.

- `**packaging**`: The type of the artifact. Defaults to `jar` if omitted. Other common values are `war`, `pom`, or `ear`
- `**classifier**`: An arbitrary string appended to the version to distinguish artifacts built from the same POM but with different content. _Common examples:_ `javadoc` (the documentation jar), `sources` (the source code jar), `jdk15` (compiled for a specific Java version).

**The Directory Map (How Maven finds files)  
**This is the most critical technical detail to understand. Maven Coordinates are not just abstract labels; they translate directly to a **folder structure** on your hard drive (in your local repository).  
Maven converts the `groupId` dots into folder slashes.  
**Formula:** `~/.m2/repository` + `groupId (slashes)` + `artifactId` + `version` + `filename`

**Example Mapping:** If you request the following coordinate:

- **Group:** `com.example.payment`
- **Artifact:** `processor`
- **Version:** `1.5.0`

Maven will look for the file in this exact path: `~/.m2/repository/com/example/payment/processor/1.5.0/processor-1.5.0.jar`

When you add a dependency to your `pom.xml`, you are simply telling Maven which coordinates to fetch.

```
<dependency>  
    <groupId>org.apache.commons</groupId>    
     <artifactId>commons-lang3</artifactId>   
     <version>3.12.0</version>                
</dependency>
```

### Maven Snapshots vs releases

In the world of Maven, the distinction between a **SNAPSHOT** and a **Release** is the difference between a “work in progress” and a “final product.”

- **Release Versions (e.g.,** `**1.0.0**`**):** These are **Immutable**. Once you release version `1.0.0` to a repository (like Nexus or Central), you are never allowed to change it. If you find a bug, you must release `1.0.1`. Maven assumes that if it has `1.0.0` in your local `~/.m2` folder, it never needs to check the remote server again.
- **SNAPSHOT Versions (e.g.,** `**1.0.0-SNAPSHOT**`**):** These are **Mutable**. This version indicates "development in progress." The code behind `1.0.0-SNAPSHOT` can change 50 times a day. Maven knows that the copy it has locally might be outdated.

Imagine you are working on **Team A** (Backend) and you depend on a library built by **Team B** (Core Utils). **Without SNAPSHOTs** Team B would have to release `1.1`, then `1.2`, then `1.3` every time they fixed a small bug just so Team A could download the changes. This creates "version inflation" and chaos. **With SNAPSHOTs,** Team B sets their version to `1.0.0-SNAPSHOT`. Team A depends on `1.0.0-SNAPSHOT`. Every time Team B builds, they overwrite the previous snapshot. Team A automatically gets the latest code without changing the version number in their `pom.xml`.

When you deploy a SNAPSHOT to a remote repository, Maven doesn’t actually overwrite the file named `myapp-1.0.0-SNAPSHOT.jar`. Instead, it uses **timestamping**.

If you look inside a remote repository (like Nexus), the folder for `1.0.0-SNAPSHOT` will contain files that look like this:

- `myapp-1.0.0-20231027.100000-1.jar` (Build #1)
- `myapp-1.0.0-20231027.110000-2.jar` (Build #2)
- `maven-metadata.xml`

`**maven-metadata.xml**` is the key. It acts as a pointer. It tells Maven: _"Even though the user asked for 1.0.0-SNAPSHOT, the actual latest file is Build #2."_

By default, Maven usually checks for SNAPSHOT updates **once per day**. This often leads to the “It works on my machine” problem, where a colleague pushed a fix an hour ago, but your Maven thinks it’s still up to date.

==To force Maven to ignore its local cache and check for new SNAPSHOTs immediately, you use the== ==`-U`== ==flag==

```
mvn clean install -U
```

Never use SNAPSHOT dependencies in a production release.

### Maven repositories

In the Maven universe, a **Repository** is simply a directory where all the project jars, library jars, plugins, and other artifacts are stored

Think of it as a **warehouse** for your dependencies. Instead of keeping a `lib/` folder in every single project (which wastes space and causes version conflicts), Maven stores them all in one organized place.

There are three strictly defined types of repositories.

**The Local Repository (Your Cache)**

- **Location:** On your machine. usually at `~/.m2/repository` (Mac/Linux) or `C:\Users\{your-username}\.m2\repository` (Windows).
- **Purpose:** This is a cache. Maven _always_ looks here first.
- **How it works:** When you build a project, Maven checks if the dependencies are in your Local Repo.
- **If Yes:** It uses them directly. No internet needed.
- **If No:** It downloads them from a Remote Repo and saves them here for next time.

**The Central Repository (The Public Source)**

- **Location:** Hosted on the internet by the Maven community (repo.maven.apache.org).
- **Purpose:** The default place Maven looks if it can’t find a dependency locally.
- **Content:** It contains millions of open-source libraries (Spring, Hibernate, Apache Commons, etc.).
- **Configuration:** You don’t need to configure this; it is built into Maven.

**The Remote / Internal Repository (The Enterprise Hub)**

- **Location:** Hosted on a server inside your company’s network or cloud.
- **Proxy:** It proxies the Central Repository. Instead of 100 developers downloading “Spring Boot” from the internet 100 times, the Remote Repo downloads it once, and everyone else downloads it from the internal server (faster, saves bandwidth).
- **Hosting Private Artifacts:** If your team writes a library (`my-company-utils.jar`) that is proprietary, you can't upload it to the public Central Repo. You upload it here so other teams at your company can use it.
- **Software:** Common tools to manage this include **Sonatype Nexus** or **JFrog Artifactory**.

When you run `mvn install`, Maven follows a strict lookup order:

Look in the **Local Repository → (if not found) →** Look in the **Remote/Central Repository → (if not found) →**The build fails with an error: `Could not resolve dependencies`.

While Central is default, you often need to tell Maven about your company’s private repository. ==This is usually done in the== ==`settings.xml`== ==file (global configuration) or the== ==`pom.xml`== ==(project configuration).==

```
<repositories>  
    <repository>  
        <id>my-internal-repo</id>  
        <url>http://repo.mycompany.com/maven2</url>  
    </repository>  
</repositories>
```

### ==Maven wagon==

**Maven Wagon** is the transport abstraction layer of Apache Maven. It is the mechanism Maven uses to move artifacts (files) to and from remote repositories.

Maven needs to download dependencies and upload build artifacts to various servers. However, different servers speak different languages (protocols). One server might require **HTTP,** Another might require **SSH/SCP,** Another might be an AWS **S3** bucket.

Instead of hardcoding every possible protocol into the Maven core, the developers created an interface called **Wagon**. If you need to talk to a new type of server, you just plug in a new “Wagon Provider.”

Maven includes some wagons by default, but others must be added explicitly.

- **HTTP / HTTPS:** The default. Used for connecting to Maven Central and most enterprise repositories. (Note: As of Maven 3.9.0, the default HTTP transport has shifted to a newer native resolver, but Wagon is still the underlying concept for other protocols).
- **File:** Used for moving files to a repository on the local hard drive.
- **SSH / SCP:** Used to upload artifacts securely to a remote Linux server using SSH keys.
- **FTP:** File Transfer Protocol (less common now but supported).
- **WebDAV:** An extension of HTTP often used by older repository managers.

You rarely interact with Wagon directly; it usually works in the background. However, there are two common scenarios where you must configure it explicitly.

### Scenario A: Deploying to a Non-Standard Server (e.g., AWS S3)

If your team uses an S3 bucket as a private Maven repository, Maven doesn’t know how to speak “S3” out of the box. You must add the S3 Wagon extension to your `pom.xml`.

```
<build>  
    <extensions>  
        <extension>  
            <groupId>com.github.seahen</groupId>  
            <artifactId>maven-s3-wagon</artifactId>  
            <version>1.3.3</version>  
        </extension>  
    </extensions>  
</build>  
  
<distributionManagement>  
    <repository>  
        <id>my-s3-repo</id>  
        <url>s3://my-company-bucket/release</url>  
    </repository>  
</distributionManagement>
```

### Scenario B: The `wagon-maven-plugin`

Sometimes you want to just upload or download a file without running a full build. The **Wagon Maven Plugin** allows you to use Wagon as a standalone tool.

```
# Example: Upload a file to a server using SCP  
mvn wagon:upload-single \  
   -Durl=scp://myserver.com/var/www/html \  
   -DfromFile=target/myapp.war \  
   -DserverId=myserver
```

Note: For years, Maven used Wagon for _everything_. However, Wagon had some performance limitations with HTTP/2. Starting with **Maven 3.9.0**, the default transport for **HTTP/HTTPS** was switched from Wagon to a new **Native Resolver** (based on `java.net.http`).

### Maven Project Object Model (POM)

pom.xml is an XML document which describes a maven project. It must comply with maven-4.0.0.xsd : the XML schema defining the rules for the XML document

POMs can also inherit properties from a parent POM. Similarly in a multi module project, sub modules can inherit the properties from the parent or top level pom

In Maven, what you see is rarely what you get. You might look at your project’s `pom.xml` and see 20 lines of configuration, but when Maven runs, it executes a configuration that is thousands of lines long.

One very useful tool for debugging is the Effective POM — it is the POM complete with all inherited propertes. It is the final, merged XML configuration that Maven actually uses to execute a build. It is the result of a mathematical aggregation of several different sources of configuration. Think of your `pom.xml` as just the "tip of the iceberg." The Effective POM is the entire iceberg.

To generate the effective pom:

```
mvn help:effective-pom
```

To save it to a file (highly recommended for reading):

```
mvn help:effective-pom -Doutput=effective-pom.xml
```

You typically don’t need the Effective POM when things are going well. You need it when things are going wrong. The **Effective POM** is the single source of truth for your build. It removes the magic of inheritance and defaults, exposing the raw XML that Maven is actually processing. Whenever you find yourself asking, _“Why is Maven doing X when I didn’t tell it to?”_, the answer is almost always waiting for you in `mvn help:effective-pom`.

### Maven Dependencies

A dependency is simply an external Java library (JAR) that your project needs to compile, test, or run. Instead of downloading the JAR manually, you tell Maven the **Coordinates** (Group ID, Artifact ID, and Version), and Maven handles the rest.

A standard dependency declaration in your `pom.xml` looks like this:

```
<dependencies>  
    <dependency>  
        <groupId>com.fasterxml.jackson.core</groupId>   
        <artifactId>jackson-databind</artifactId>       
        <version>2.15.2</version>                       
        <scope>compile</scope>                          
    </dependency>  
</dependencies>
```

The `<scope>` tag tells Maven **when** to add the JAR to the classpath. If you choose the wrong scope, your application might crash at runtime with a `ClassNotFoundException` or become bloated with unnecessary files.

Here are the 6 scopes you need to know:

1. compile  
    **Visibility:** Available everywhere (Compilation, Testing, Running)  
    **Transitive:** Yes. (If Project A depends on B, anyone who depends on A also gets B).  
    **Use Case:** Standard libraries like `commons-lang3`, `spring-core`, or `guava`
2. provided  
    **Visibility:** Available for Compilation and Testing, but **NOT** added to the final runtime artifact. Typically, because you expect the environment (like the JDK or a Web Server) to provide it.  
    **Use Case:** The Servlet API (`javax.servlet-api`). Tomcat already has this JAR inside it. If you bundle it in your WAR file, the two versions will conflict and crash the server.
3. runtime  
    **Visibility:** NOT available for Compilation, but available for Testing and Running. (You code against an interface, but you need the implementation at runtime).  
    **Use Case:** JDBC Drivers (e.g., `mysql-connector-java`). You shouldn't be using MySQL classes directly in your code (you use standard JDBC interfaces), but the driver must be there when the app starts
4. test  
    **Visibility:** Only available during the compilation and execution of tests  
    **Transitive:** No  
    **Use Case:** `junit`, `mockito`, `assertj`. These should never end up in your production build
5. ==system==  
    **Visibility:** Similar to `provided`, but you must explicitly provide a path to the JAR on your local disk.  
    **Warning:** **Avoid this.** It makes your build non-portable (it breaks on other people’s machines).
6. import  
    **Visibility:** Only used in the `<dependencyManagement>` section.  
    **Use Case:** Importing a “BOM” (Bill of Materials) like `spring-boot-dependencies` to manage versions for you.

Maven is recursive. If you add **Spring Boot Web** as a dependency, you don’t just get one JAR. You get the JAR, plus its dependencies, plus _their_ dependencies.

- **Direct Dependency:** The one you listed in your POM.
- **Transitive Dependency:** The dependencies required by your direct dependency.

**The “Dependency Hell” Problem  
**What happens if Library A needs `log4j` version 1.2, but Library B needs `log4j` version 2.0? Maven resolves this using a **"Nearest Wins"** strategy. It uses the version closest to your project in the dependency tree.

Best Practice: If you have version conflicts, use `mvn dependency:tree` to visualize the conflict, and then use the `<exclusions>` tag to manually block the unwanted transitive dependency.

```
<dependency>  
    <groupId>com.example</groupId>  
    <artifactId>legacy-library</artifactId>  
    <version>1.0.0</version>  
    <exclusions>  
        <exclusion>  
            <groupId>log4j</groupId> <artifactId>log4j</artifactId>  
        </exclusion>  
    </exclusions>  
</dependency>
```

Unused dependencies bloat your application and slow down startup. Occasionally run:

```
mvn dependency:analyze
```

This command will report:

- “Used undeclared dependencies” (Dangerous! You are using a transitive JAR directly).
- “Unused declared dependencies” (Bloat! You can delete these).

### Maven Build Lifecycles

**The Three Built-in Lifecycles  
**Maven comes with three completely independent lifecycles. When you run a Maven command, you are triggering one of these three:

1. `**clean**` **Lifecycle:** Handles project cleaning (deleting old builds).
2. `**default**` **Lifecycle:** Handles the actual build and deployment (the one you use 99% of the time).
3. `**site**` **Lifecycle:** Handles the creation of project documentation (HTML reports).

**The** `**default**` **Lifecycle (The Main Event)**This is the core of Maven. It consists of **23 distinct phases**, but you typically only deal with the “Big 7.” Here is the sequence. **Crucially, if you run a later phase, all previous phases run automatically.**

**The Sequence:**

1. `**validate**`: Checks if the project is correct and all necessary information (like `pom.xml`) is available.
2. `**compile**`: Translates your `.java` files in `src/main/java` into `.class` files in `target/classes`.
3. `**test**`: Runs unit tests (e.g., JUnit) located in `src/test/java`. These tests should not require the code be packaged or deployed.
4. `**package**`: Takes the compiled code and puts it into its distributable format, such as a JAR or WAR.
5. `**verify**`: Runs integration tests and performs checks to ensure quality criteria are met. This is often where plugins like Checkstyle or Jacoco run.
6. `**install**`: Installs the package into the **Local Repository** (`~/.m2/repository`), making it available as a dependency for other projects locally.
7. `**deploy**`: Copies the final package to the **Remote Repository** (e.g., Nexus, Artifactory) for sharing with other developers and teams.

e.g. If you run: mvn test, Maven executes: `validate` -> `compile` -> `test`.  
If you run: mvn install, Maven executes: `validate` -> `compile` -> `test` -> `package` -> `verify` -> `install`.

**Phases vs. Goals (The Mechanics)  
**This is the most common point of confusion.

- **A Phase** is just a step in the lifecycle (an abstract concept like “Compile”). It doesn’t actually _do_ anything by itself.
- **A Goal** is a specific task provided by a Plugin (the actual worker).

Maven binds **Goals** to **Phases**. Example: When the `**compile**` **phase** triggers, Maven looks for a plugin goal bound to it. By default, the `maven-compiler-plugin:compile` goal is bound to this phase.

- **Phase:** `compile` (The "When")
- **Goal:** `compiler:compile` (The "What")

You can hack the lifecycle by binding extra goals to phases. For example, you can bind the `docker:build` goal to the `package` phase so that a Docker image is built every time a JAR is packaged.

**The** `**clean**` **Lifecycle**This is simple but essential. It has three phases:

- `pre-clean`
- `**clean**`: Removes all files generated by the previous build (deletes the `target/` directory).
- `post-clean`

**The** `**site**` **Lifecycle**Maven can generate a website for your project, including Javadocs, unit test reports, and dependency graphs.

- `pre-site`
- `**site**`: Generates the site documentation.
- `post-site`
- `site-deploy`: Deploys the generated site to a server.

The Maven Lifecycle is a state machine. It guarantees reproducibility. Whether you run the build on your laptop or on a CI/CD server like Jenkins, the steps (`compile` -> `test` -> `package`) happen in the exact same order, ensuring consistent results.

### Maven Wrapper

**Maven Wrapper** is a utility that embeds a specific version of Maven directly into your project. Think of it as “bundling the build tool with the source code.” Instead of relying on the version of Maven installed on your computer (which might be different from your colleague’s), the project itself carries a script that knows exactly which version of Maven it needs and downloads it automatically if it’s missing. It helps you get rid of “It Works on My Machine” problem

The Maven Wrapper solves this by ensuring **everyone uses the exact same maven version**. When you use the wrapper, you don’t run the `mvn` command installed on your OS. Instead, you run a script called `mvnw` (Maven Wrapper) that lives inside your project folder.

- **If you have the correct Maven version:** It runs the build.
- **If you don’t:** It automatically downloads the specific Maven version defined in the project settings, installs it into a private cache, and _then_ runs the build

When you add the wrapper to your project, it creates these files:

- `**mvnw**` (Linux/Mac script): The executable you run instead of `mvn`.
- `**mvnw.cmd**` (Windows script): The executable for Windows users.
- `**.mvn/wrapper/maven-wrapper.properties**`: The configuration file where you define the version (e.g., `distributionUrl=...maven-3.9.6-bin.zip`).

To add the wrapper to an existing Maven project, run this command one time:

```
mvn wrapper:wrapper -Dmaven=3.9.6
```

This will generate the `mvnw` scripts and the `.mvn` folder. You then commit these files to Git so everyone else gets them. Once installed, you simply swap `mvn` for `./mvnw` in your commands:

- **Standard:** `mvn clean install`
- **Wrapper:** `./mvnw clean install` (Mac/Linux) or `mvnw clean install` (Windows)

### Maven Archetypes

If Maven is the factory that builds your software, **Archetypes** are the blueprints.

Starting a new project from zero is tedious. You have to create the folder structure (`src/main/java`), set up the `pom.xml`, add the JUnit dependencies, and configure the compiler plugins. Doing this manually every time is a violation of the DRY (Don't Repeat Yourself) principle.

An **Archetype** is a project templating toolkit. It allows you to generate a fully functional, empty project skeleton with a single command.

You generate a project using the `archetype:generate` goal.

```
mvn archetype:generate
```

Maven will present a massive list of numbered archetypes. You can type `quickstart` to filter the list and then select options interactively

You can provide all arguments in one line to skip the interactive wizard. This is how CI/CD pipelines generate projects.

```
mvn archetype:generate \  
    -DgroupId=com.example.finance \  
    -DartifactId=trade-engine \  
    -Dversion=1.0.0-SNAPSHOT \  
    -DarchetypeArtifactId=maven-archetype-quickstart \  
    -DinteractiveMode=false
```

While there are thousands of archetypes available, 95% of the time you will use one of these three:

- maven-archetype-quickstart  
    **The Standard:** This is the default. It creates a simple JAR project  
    **Contains:** A generic `pom.xml`, a basic `App.java` ("Hello World"), and a `AppTest.java` (JUnit).  
    **Use Case:** Libraries, utilities, or simple standalone apps.
- maven-archetype-webapp  
    **The Web Legacy:** Creates a standard Java Web Application structure.  
    **Contains:** A `src/main/webapp` folder, a `WEB-INF/web.xml` file, and packaging set to `<packaging>war</packaging>`.  
    **Use Case:** Traditional Servlet/JSP applications deployed to Tomcat or WildFly.
- maven-archetype-plugin  
    **The Extender:** Creates a project set up to build a custom Maven Plugin.  
    **Use Case:** When you want to write your own build logic to hook into the Maven lifecycle.

## ==Common Maven Plugins==

Since Maven is a plugin-execution framework, your build is defined entirely by the plugins you use. While the core plugins (`compiler`, `surefire`, `jar`) are automatic, there is a "power set" of plugins that advanced developers use to manage complex projects. Here is a breakdown of commonly used Maven plugins, categorized by the problem they solve.

### The Core Lifecycle Plugins (The “Must-Haves”)

These are the plugins that handle the core heavy lifting of your build.

**maven-compiler-plugin  
**Compiles your Java code. It binds to the `compile` and `test-compile` phases of the build lifecycle.  
_Key Config:_ Setting the `source` and `target` (or the newer `release`) version to match your JDK (e.g., 17 or 21).

```
<build>  
    <plugins>  
      <plugin>  
        <groupId>org.apache.maven.plugins</groupId>  
        <artifactId>maven-compiler-plugin</artifactId>  
        <version>3.11.0</version>  
        <configuration>  
          <release>17</release> </configuration>  
      </plugin>  
    </plugins>  
  </build>
```

To keep your `pom.xml` clean, it is best practice to define the version numbers in the `<properties>` section rather than hardcoding them inside the plugin block. Maven automatically looks for these specific property names.

```
<project>  
  ...  
  <properties>  
    <maven.compiler.release>17</maven.compiler.release>  
   </properties>  
  
  <build>  
    <plugins>  
      <plugin>  
        <groupId>org.apache.maven.plugins</groupId>  
        <artifactId>maven-compiler-plugin</artifactId>  
        <version>3.11.0</version>  
      </plugin>  
    </plugins>  
  </build>  
  ...  
</project>
```

While Maven uses a default compiler version (often quite old, like Java 1.5 or 1.6 in older Maven versions), you almost always need to configure this plugin to tell Maven which Java version you are using.

**maven-resources-plugin  
**The `maven-resources-plugin` handles the copying of project resources (non-code files like properties, XML, images, or configuration files) to your output directory.

It binds to the `process-resources` phase (for main resources) and the `process-test-resources` phase (for test resources). It essentially moves files from `src/main/resources` to `target/classes`.

Here is a standard configuration that enables **filtering** (replacing variables like `${app.version}` with actual values) and sets the **encoding**.

```
<project>  
  ...  
  <build>  
    <plugins>  
      <plugin>  
        <groupId>org.apache.maven.plugins</groupId>  
        <artifactId>maven-resources-plugin</artifactId>  
        <version>3.3.1</version>  
        <configuration>  
          <encoding>UTF-8</encoding>            
          <escapeString>\</escapeString>  
        </configuration>  
      </plugin>  
    </plugins>  
  
    <resources>  
      <resource>  
        <directory>src/main/resources</directory>  
        <filtering>true</filtering> </resource>  
    </resources>  
  </build>  
  ...  
</project>
```

Filtering (`<filtering>true</filtering>`) is the most powerful feature of this plugin. When filtering is enabled, Maven scans text files in your resource directory for placeholders like `${name}` and replaces them with values defined in your `pom.xml` properties.

Example Source File (`src/main/resources/app.properties`):

```
application.name=${project.name}  
application.version=${project.version}
```

Result in Output (`target/classes/app.properties`):

```
application.name=My Cool App  
application.version=1.0.0
```

By default, Maven only looks in `src/main/resources`. You can add more directories (e.g., if you have a separate folder for config files) using the `<resources>` block.

```
<build>  
    <resources>  
        <resource>  
            <directory>src/main/resources</directory>  
            <filtering>true</filtering>  
        </resource>  
        <resource>  
            <directory>src/main/bin</directory>  
            <filtering>false</filtering>  
        </resource>  
    </resources>  
</build>
```

You can control exactly which files are copied using glob patterns.

```
<resource>  
    <directory>src/main/resources</directory>  
    <excludes>  
        <exclude>**/*.psd</exclude> </excludes>  
    <includes>  
        <include>**/*.xml</include>  
        <include>**/*.properties</include>  
    </includes>  
</resource>
```

You can control the encoding globally using a property, which the `maven-resources-plugin` (and others) will pick up automatically.

```
<properties>  
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>  
</properties>
```

**maven-clean-plugin  
**The `maven-clean-plugin` is the utility responsible for resetting your project to its initial state. It is the primary plugin bound to the `**clean**` **lifecycle**.

By default, its only job is to attempt to delete the `target` directory (where all compiled classes, JARs, and WARs live).

In most projects, you do not need to configure this plugin extensively. You simply define the version to ensure build stability.

```
<project>  
  ...  
  <build>  
    <plugins>  
      <plugin>  
        <groupId>org.apache.maven.plugins</groupId>  
        <artifactId>maven-clean-plugin</artifactId>  
        <version>3.3.2</version>  
      </plugin>  
    </plugins>  
  </build>  
  ...  
</project>
```

**Command:** `mvn clean` **Result:** Deletes the `/target` folder.

**Packaging Plugins (Creating the Artifact)**

**maven-jar-plugin**  
The `maven-jar-plugin` is the default plugin responsible for taking your compiled class files (`target/classes`) and resources and packaging them into a **JAR (Java Archive)** file.

While it runs automatically in the `package` phase, you often need to configure it explicitly to customize the `MANIFEST.MF` file, which controls how the JAR behaves (e.g., making it executable).

It is important to note that `**maven-jar-plugin**` **creates "Skinny JARs"**. The produced artifact contains _only_ your code. It does **not** include your dependencies (Spring, Apache Commons, etc.).

This is the most common custom configuration. It allows you to run your JAR using `java -jar app.jar`, assuming your dependencies are located in a standard `lib/` folder next to the JAR

```
<build>  
    <plugins>  
        <plugin>  
            <groupId>org.apache.maven.plugins</groupId>  
            <artifactId>maven-jar-plugin</artifactId>  
            <version>3.3.0</version>  
            <configuration>  
                <archive>  
                    <manifest>  
                        <mainClass>com.example.myproject.MainApp</mainClass>                          
                        <!-- This adds a Class-Path header to the Manifest. -->  
                        <addClasspath>true</addClasspath>  
                        <!-- This tells the JAR where to look for those dependencies.  -->  
                        <classpathPrefix>lib/</classpathPrefix>  
                    </manifest>  
                </archive>                  
                <excludes>  
                    <exclude>**/application.properties</exclude>  
                </excludes>  
            </configuration>  
        </plugin>  
    </plugins>  
</build>
```

Use the `maven-jar-plugin` when you are building a library for others to use, or when you are building a traditional application where dependencies are managed separately (in a `lib` folder).

**maven-war-plugin  
**While the `maven-jar-plugin` is the standard for libraries and microservices, the `**maven-war-plugin**` is the heavy lifter for traditional Java Web Applications.

Its job is to collect your compiled classes, your internal resources, your external dependencies, and your static web assets (HTML, CSS, JSP), and bundle them into a **WAR (Web Application Archive)** file ready for deployment to an application server like Tomcat, WildFly, or Jetty.

Unlike a JAR, a WAR has a strict internal structure required by the Java Servlet Specification. The plugin automates the mapping of your source folders to this structure.

- `**src/main/java**` → Compiles to `WEB-INF/classes`
- `**src/main/resources**` → Copies to `WEB-INF/classes`
- **Dependencies (in POM)** → Copies to `WEB-INF/lib`
- `**src/main/webapp**` → Copies to the root of the WAR. This is where your public assets (index.html, images) and the `WEB-INF` folder live.

To use the plugin, you typically just change the packaging type in your `pom.xml`. You often don't even need to declare the plugin explicitly if you are happy with the defaults.

```
<project>  
  ...  
  <packaging>war</packaging>  
  ...  
</project>
```

However, modern development often requires customization, which is where the plugin configuration comes in.

In the legacy days (Servlet 2.5 and older), a `WEB-INF/web.xml` file was mandatory. If you tried to build a WAR without it, Maven would fail.

In modern Java (Servlet 3.0+ / Spring Boot deployed as WAR), configurations are often done via Java Annotations, so `web.xml` is optional. The most common configuration is telling Maven **not** to panic if `web.xml` is missing.

```
<build>  
    <plugins>  
        <plugin>  
            <groupId>org.apache.maven.plugins</groupId>  
            <artifactId>maven-war-plugin</artifactId>  
            <version>3.4.0</version>  
            <configuration>  
               ==<====failOnMissingWebXml====>====false====</====failOnMissingWebXml====>==                  
                <warName>ROOT</warName>  
            </configuration>  
        </plugin>  
    </plugins>  
</build>
```

**maven-shade-plugin  
**Here is a detailed breakdown of the `maven-shade-plugin`, which is the industry standard for creating "Uber-JARs" (Fat JARs) in the Maven ecosystem.

Most developers think this plugin is just for packing dependencies. However, the term **“Shade”** actually refers to its ability to **rename packages** (relocate classes) during the build process to avoid classpath conflicts.

Its two main functions are:

1. **Uber-JAR Creation:** Unpacking all your dependencies and repacking them into a single runnable JAR.
2. **Relocation:** Renaming a dependency (e.g., `com.google.guava`) to a private package (e.g., `hidden.guava`) so your library doesn't crash other applications that use a different version of Guava.

**Sample Config 1: The “Fat JAR” (Standard Use Case)**  
This configuration creates a single executable JAR containing your code and all dependencies.  
**Crucial Detail:** You must use **Transformers**. When you merge multiple JARs, they all have their own `META-INF/MANIFEST.MF` and `META-INF/services` files. If you just overwrite them, things break. Transformers merge them intelligently.

```
<build>  
    <plugins>  
        <plugin>  
            <groupId>org.apache.maven.plugins</groupId>  
            <artifactId>maven-shade-plugin</artifactId>  
            <version>3.5.1</version>  
            <executions>  
                <execution>  
                    <phase>package</phase>  
                    <goals>  
                        <goal>shade</goal>  
                    </goals>  
                    <configuration>  
                        <transformers>  
                            <transformer implementation="org.apache.maven.plugins.shade.resource.ManifestResourceTransformer">  
                                <mainClass>com.example.myproject.App</mainClass>  
                            </transformer>                              
                            <transformer implementation="org.apache.maven.plugins.shade.resource.ServicesResourceTransformer"/>  
                        </transformers>  
                          
                        <filters>  
                            <filter>  
                                <artifact>*:*</artifact>  
                                <excludes>  
                                    <exclude>META-INF/*.SF</exclude>  
                                    <exclude>META-INF/*.DSA</exclude>  
                                    <exclude>META-INF/*.RSA</exclude>  
                                </excludes>  
                            </filter>  
                        </filters>  
                    </configuration>  
                </execution>  
            </executions>  
        </plugin>  
    </plugins>  
</build>
```

**Sample Config 2: Relocation (Advanced Use Case)  
**==If you are building a library that depends on== ==`commons-collections`====, but you don't want to force your users to use== ==_your_== ==version of it, you can "shade" (rename) it inside your JAR.==

This modifies the bytecode of your classes to point to the new package name.

```
<configuration>  
    <relocations>  
        <relocation>  
            <pattern>org.apache.commons.collections</pattern>  
            <shadedPattern>com.mycompany.hidden.commons.collections</shadedPattern>  
        </relocation>  
    </relocations>  
</configuration>
```

_Result:_ Your code now imports `com.mycompany.hidden...` instead of `org.apache...`, effectively making the dependency private to your JAR.

### Summary Checklist

1. **Phase:** Always bind to the `package` phase.
2. **Signatures:** Always exclude `META-INF/*.SF` and `*.RSA` (security signatures from other JARs will invalidate your new Uber-JAR).
3. **Services:** Always use the `ServicesResourceTransformer` if your dependencies use Java SPI (like JDBC drivers or logging frameworks).

**rpm-maven-plugin  
**It allows you to map your Java artifacts (JARs, WARs), configuration files, and scripts into a Linux RPM package structure

This plugin typically requires the `rpm` or `rpmbuild` tool to be installed on the system running the build. If you are building on **Windows or macOS**, you may need to install these tools or use a "Pure Java" alternative like `rpm-builder` (though the MojoHaus plugin is the industry standard).

This configuration bundles a JAR file into `/opt/myapp/lib`, places a config file in `/etc/myapp`, and sets up file permissions.

```
<project>  
  ...  
  <build>  
    <plugins>  
      <plugin>  
        <groupId>org.codehaus.mojo</groupId>  
        <artifactId>rpm-maven-plugin</artifactId>  
        <version>2.3.0</version>  
        <extensions>true</extensions>  
        <executions>  
          <execution>  
            <id>generate-rpm</id>  
            <goals>  
              <goal>rpm</goal>  
            </goals>  
          </execution>  
        </executions>  
        <configuration>  
          <name>my-cool-app</name>  
          <group>Application/Internet</group>  
          <needarch>noarch</needarch>  
            
          <packager>DevTeam</packager>  
            
          <!-- Defines dependencies that yum or dnf will check for (e.g., ensuring Java is installed).-->  
          <requires>  
            <require>java >= 17</require>  
          </requires>  
  
          <!-- This is the core of the plugin -->  
          <!-- It defines "Take file X from my Maven project and put it in folder Y on the Linux system."  -->           
          <mappings>  
            <mapping>  
              <directory>/opt/myapp/lib</directory>  
              <filemode>644</filemode>  
              <username>appuser</username>  
              <groupname>appgroup</groupname>  
              <sources>  
                <source>  
                  <location>target/${project.artifactId}-${project.version}.jar</location>  
                </source>  
              </sources>  
            </mapping>  
  
            <mapping>  
              <directory>/etc/myapp</directory>  
              <!-- If you mark a mapping as configuration RPM is smart enough not to overwrite it if the user has modified it on the production server (it creates a .rpmnew file instead).-->  
              <configuration>true</configuration> <filemode>640</filemode>  
              <username>appuser</username>  
              <groupname>appgroup</groupname>  
              <sources>  
                <source>  
                  <location>src/main/resources/application.properties</location>  
                </source>  
              </sources>  
            </mapping>  
  
            <mapping>  
              <directory>/usr/bin</directory>  
              <filemode>755</filemode>  
              <username>root</username>  
              <groupname>root</groupname>  
              <sources>  
                <source>  
                  <location>src/main/scripts/start-app.sh</location>  
                </source>  
              </sources>  
            </mapping>  
          </mappings>  
  
          <!-- Shell scripts that run before or after the RPM installation (useful for creating users, restarting services, etc.)-->  
          <preinstallScriptlet>  
            <script>echo "Preparing to install..."</script>  
          </preinstallScriptlet>  
          <postinstallScriptlet>  
            <script>              useradd appuser || true  
              chown -R appuser:appgroup /opt/myapp            </script>  
          </postinstallScriptlet>  
  
        </configuration>  
      </plugin>  
    </plugins>  
  </build>  
  ...  
</project>
```

Once configured, you can generate the RPM by running:

```
# (If you included the <executions> block bound to the package phase)  
mvn package
```

or:

```
mvn rpm:rpm
```

The output file will be located in `target/rpm/[project-name]/RPMS/noarch/`.

**maven-source-plugin  
**The `maven-source-plugin` is one of the most important plugins for "developer experience." Its sole purpose is to bundle your `.java` files into a zip file (a JAR) and attach it to your build.

This allows other developers who use your library to **Ctrl+Click** into your code in their IDE (IntelliJ/Eclipse) and see the actual source code and Javadocs instead of just the compiled `.class` bytecode.

When you run a build, this plugin creates a second artifact alongside your main JAR.

- **Main Artifact:** `my-app-1.0.jar` (Compiled code)
- **Source Artifact:** `my-app-1.0-sources.jar` (Source code)

When you run `mvn install` or `mvn deploy`, both files are uploaded to the repository.

By default, this plugin does not run. You must explicitly bind it to the build lifecycle. The standard practice is to bind it to the `**verify**` phase (so sources are generated right before installation).

```
<build>  
    <plugins>  
        <plugin>  
            <groupId>org.apache.maven.plugins</groupId>  
            <artifactId>maven-source-plugin</artifactId>  
            <version>3.3.0</version>  
            <executions>  
                <execution>  
                    <id>attach-sources</id>  
                    <phase>verify</phase>  
                    <goals>  
                        <goal>jar-no-fork</goal>  
                    </goals>  
                </execution>  
            </executions>  
        </plugin>  
    </plugins>  
</build>
```

**jar-no-fork** **vs** **jar**:

- `**jar**`: This older goal creates a "forked" lifecycle. It basically restarts the build process from the beginning to ensure sources are fresh. This is often unnecessary and slow.
- `**jar-no-fork**`: The modern standard. It assumes the sources in `src/main/java` are already up to date and just packages them. It is much faster.

The plugin “attaches” the source JAR to the project object model. This means when `maven-install-plugin` runs later, it "sees" this extra file and installs it into `~/.m2` automatically.

**maven-assembly-plugin  
**The `maven-assembly-plugin` is used to aggregate your project's output (JARs/WARs) along with its dependencies, documentation, scripts, and configuration files into a single distributable archive (like a `.zip`, `.tar.gz`, or a "Fat JAR").

Unlike the Shade plugin (which merges everything into one JAR), the Assembly plugin is best used when you want to create a specific folder structure for distribution (e.g., a zip file containing a `bin/` folder for scripts and a `lib/` folder for dependencies).

To use this plugin effectively, you typically need two things:

1. **POM Configuration:** Tells Maven to run the plugin.
2. **Assembly Descriptor:** An XML file (usually in `src/assembly/`) that defines exactly how the archive should look.

**The POM Configuration (**`**pom.xml**`**)  
**This configuration binds the assembly goal to the `package` phase, so the distribution file is created automatically when you run `mvn package`.

```
<project>  
  ...  
  <build>  
    <plugins>  
      <plugin>  
        <groupId>org.apache.maven.plugins</groupId>  
        <artifactId>maven-assembly-plugin</artifactId>  
        <version>3.7.1</version>  
        <configuration>  
          <descriptors>  
            <descriptor>src/assembly/distribution.xml</descriptor>  
          </descriptors>  
          <archive>  
            <manifest>  
              <mainClass>com.example.MyApp</mainClass>  
            </manifest>  
          </archive>  
        </configuration>  
        <executions>  
          <execution>  
            <id>make-assembly</id>  
            <phase>package</phase> <goals>  
              <goal>single</goal>  
            </goals>  
          </execution>  
        </executions>  
      </plugin>  
    </plugins>  
  </build>  
  ...  
</project>
```

**The Assembly Descriptor (**`**src/assembly/distribution.xml**`**)  
**This file defines the layout of the final ZIP file. This example creates a standard distribution structure:

- `**/bin**`: Contains shell scripts (with executable permissions).
- `**/lib**`: Contains all runtime JAR dependencies.
- `**/conf**`: Contains configuration file

```
<assembly xmlns="http://maven.apache.org/ASSEMBLY/2.2.0"  
    xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"  
    xsi:schemaLocation="http://maven.apache.org/ASSEMBLY/2.2.0 http://maven.apache.org/xsd/assembly-2.2.0.xsd">  
    
  <id>dist</id> <formats>  
    <format>zip</format>  
    <format>tar.gz</format> </formats>  
  
  <includeBaseDirectory>true</includeBaseDirectory>  
  
  <dependencySets>  
    <dependencySet>  
      <outputDirectory>lib</outputDirectory>  
      <useProjectArtifact>true</useProjectArtifact> <scope>runtime</scope>  
    </dependencySet>  
  </dependencySets>  
  
  <fileSets>  
    <fileSet>  
      <directory>src/main/scripts</directory>  
      <outputDirectory>bin</outputDirectory>  
      <fileMode>0755</fileMode> </fileSet>  
  
    <fileSet>  
      <directory>src/main/resources</directory>  
      <outputDirectory>conf</outputDirectory>  
      <includes>  
        <include>*.properties</include>  
        <include>*.xml</include>  
      </includes>  
    </fileSet>  
      
    <fileSet>  
      <directory>${project.basedir}</directory>  
      <outputDirectory>/</outputDirectory>  
      <includes>  
        <include>README.md</include>  
      </includes>  
    </fileSet>  
  </fileSets>  
</assembly>
```

### Utility & Dependency Management Plugins

These plugins help you manage the complexity of external libraries.

**maven-dependency-plugin  
**The `maven-dependency-plugin` is the "Swiss Army Knife" for managing, analyzing, and manipulating your project's classpath.

While plugins like `compiler` and `surefire` use dependencies implicitly, the **dependency plugin** allows you to interact with them directly: copying them to a specific folder, unpacking them, analyzing for unused libraries, or visualizing the hierarchy

This plugin is unique because it is used both **during the build** (configured in POM) and **ad-hoc** (run via command line).

- `**dependency:tree**`: Visualizes the hierarchy to debug conflicts.
- `**dependency:copy-dependencies**`: Copies all JARs from the local repository to a folder (e.g., `target/lib`).
- `**dependency:unpack**`: Extracts files from a dependency JAR (e.g., extracting native `.dll` or `.so` files).
- `**dependency:analyze**`: Scans your bytecode to find "Used but Undeclared" or "Declared but Unused" dependencies.

==A very common requirement is to distribute your JAR alongside all its dependencies in a== ==`lib/`== ==folder. The== ==`maven-jar-plugin`== ==can link to this folder in the Manifest, but the== ==`maven-dependency-plugin`== ==is what actually== ==**creates and populates**== ==that folder.==

Here is how you configure it to run automatically during the `package` phase.

```
<build>  
    <plugins>  
        <plugin>  
            <groupId>org.apache.maven.plugins</groupId>  
            <artifactId>maven-dependency-plugin</artifactId>  
            <version>3.6.1</version>  
            <executions>  
                <execution>  
                    <id>copy-libs</id>  
                    <!-- This tells Maven to run this copy operation right after the JAR is built-->  
                    <phase>package</phase>  
                    <goals>  
                        <goal>copy-dependencies</goal>  
                    </goals>  
                    <configuration>  
                        <outputDirectory>${project.build.directory}/lib</outputDirectory>                          
                        <!-- It ensures you don't bloat your distribution with test libraries (like Mockito or JUnit) that are not needed to run the application. -->  
                        <includeScope>runtime</includeScope>                          
                        <stripVersion>false</stripVersion>  
                        <overWriteReleases>false</overWriteReleases>  
                        <overWriteSnapshots>true</overWriteSnapshots>  
                        <!-- If you are working with SNAPSHOT dependencies (dev versions), this ensures you always overwrite the old JAR in the lib folder with the fresh build from the repo. -->  
                        <overWriteIfNewer>true</overWriteIfNewer>  
                    </configuration>  
                </execution>  
            </executions>  
        </plugin>  
    </plugins>  
</build>
```

You often don’t put this plugin in the POM at all. You just run it directly to solve problems.

To check for version conflicts:

```
mvn dependency:tree -Dverbose
```

To clean up your POM (find unused jars):

```
mvn dependency:analyze
```

**versions-maven-plugin  
**The `versions-maven-plugin` is the dedicated maintenance worker for your `pom.xml`.

In a modern project with 50+ dependencies, manually checking Maven Central to see if “Spring Boot” or “Jackson” has a new release is impossible. This plugin automates that discovery and, optionally, performs the upgrades for you.

It serves two main roles:

1. **Reporting:** “Tell me what is outdated.”
2. **Mutating:** “Update my version numbers automatically.”

**The Reporting Mode (Manual Usage)  
**You rarely configure this plugin to run automatically in a build. Instead, you usually run it ad-hoc from the command line to check the health of your project.

```
mvn versions:display-dependency-updates
```

**What it does:** It scans your POM, checks the remote repository for every single library, and prints a report of available upgrades.

**The Mutation Mode (Release Management)  
**This plugin is also the standard way to change your project’s own version (e.g., moving from `1.0.0-SNAPSHOT` to `1.0.0`).

Instead of opening 10 different `pom.xml` files in a multi-module project and doing "Find & Replace," you run:

```
mvn versions:set -DnewVersion=1.0.0
```

This updates the parent and all child modules instantly.

One common annoyance with the reporting tool is that it might suggest alpha or beta versions (e.g., suggesting you upgrade from `1.0.0` to `2.0.0-alpha1`).

You can configure the plugin to ignore these unstable versions using a `rules.xml` file, but for a simpler configuration, you can configure the plugin in your POM to manage how it handles backups and strictness.

Here is a configuration that disables the annoying `.versionsBackup` files (which clutter your directory) and configures the rules.

```
<build>  
    <plugins>  
        <plugin>  
            <groupId>org.codehaus.mojo</groupId>  
            <artifactId>versions-maven-plugin</artifactId>  
            ==<====version====>====2.16.2====</====version====>==  
            <configuration>  
                <generateBackupPoms>false</generateBackupPoms>  
                  
                <comparisonMethod>maven</comparisonMethod>  
                  
                <excludes>  
                    <exclude>com.legacy.vendor:broken-library</exclude>  
                </excludes>  
                  
            </configuration>  
        </plugin>  
    </plugins>  
</build>
```

To strictly ignore alpha/beta versions in the report, the plugin requires an external rule set file. However, you can use the `**dependency-updates-report**` goal within the Maven Site lifecycle to generate a graphical HTML report that filters these out.

If you just want to update dependencies via command line but ignore snapshots/alphas, you typically use:

```
mvn versions:use-latest-releases -DallowSnapshots=false
```

**maven-enforcer-plugin  
**The `maven-enforcer-plugin` is the "Health Inspector" or "Police Officer" of your build process.

Its job is to standardize the build environment. It prevents the “It works on my machine” syndrome by forcing every developer (and the CI server) to adhere to a strict set of rules. If a rule is violated, the build fails immediately.

You typically use this plugin to enforce three things:

1. **Environment:** “Everyone must use JDK 17 or higher and Maven 3.8+.”
2. **Hygiene:** “No one is allowed to use `log4j` version 1.x (security risk)."
3. **Sanity:** “No circular dependencies” or “No two dependencies can have conflicting versions.”

Here is a production-ready configuration. It ensures the environment is correct and explicitly bans a problematic library (`commons-logging`, which is often replaced by SLF4J).

```
<build>  
    <plugins>  
        <plugin>  
            <groupId>org.apache.maven.plugins</groupId>  
            <artifactId>maven-enforcer-plugin</artifactId>  
            <version>3.4.1</version>  
            <executions>  
                <execution>  
                    <id>enforce-rules</id>  
                    <goals>  
                        <goal>enforce</goal>  
                    </goals>  
                    <configuration>  
                        <rules>  
                            <requireMavenVersion>  
                                <!-- This syntax is a Range -->  
                                <!-- [3.8.1,) = 3.8.1 or anything greater (Inclusive).-->  
                                <version>[3.8.1,)</version>  
                                <message>You need Maven 3.8.1 or newer to build this!</message>  
                            </requireMavenVersion>  
                              
                            <requireJavaVersion>  
                                <version>[17,)</version>  
                                <message>This project requires JDK 17+.</message>  
                            </requireJavaVersion>  
                              
                            <bannedDependencies>  
                                <!-- his checks not just your pom.xml, but the POMs of all your dependencies. -->  
                                <searchTransitive>true</searchTransitive>  
                                <excludes>  
                                    <exclude>log4j:log4j</exclude>  
                                    <exclude>commons-logging:commons-logging</exclude>  
                                </excludes>  
                                <message>Don't use legacy logging! Use SLF4J.</message>  
                            </bannedDependencies>  
                        </rules>  
                        <!-- If set to false, the enforcer will only print a warning (Yellow text) but let the build continue. Always set to true for production builds. -->  
                        <fail>true</fail>  
                    </configuration>  
                </execution>  
            </executions>  
        </plugin>  
    </plugins>  
</build>
```

**The “Dependency Convergence” Rule  
**This is the strictest rule available. It forces **Dependency Convergence**.

**The Problem:**

- Library A needs `Gson 2.8`
- Library B needs `Gson 2.6`
- Maven usually picks one (Nearest Wins).

**The Enforcer Rule:** If you enable `<dependencyConvergence/>`, the Enforcer will **fail the build** if different versions of the same library exist anywhere in the dependency tree. It forces you to manually exclude the unwanted version or align them in `<dependencyManagement>`.

```
<rules>  
    <dependencyConvergence/>  
</rules>
```

Use the `maven-enforcer-plugin` to codify your team's best practices. Instead of writing a Wiki page that says "Please use Java 17," put it in the Enforcer plugin so the build literally won't work otherwise.

**maven-checkstyle-plugin  
**The `maven-checkstyle-plugin` is your automated code reviewer. It scans your Java source code and enforces a set of coding standards.

Unlike the compiler (which checks for errors), Checkstyle checks for **style**: indentation, naming conventions (e.g., constant names must be `UPPER_CASE`), import order, max line length, and missing Javadocs.

You define a set of rules (an XML file). When the build runs, the plugin compares your code against these rules.

- **If code passes:** The build continues.
- **If code fails:** The build can be configured to fail immediately or just generate a warning report.

**Sample Configuration: The “Strict Google Style”  
**This configuration enforces the popular **Google Java Style Guide**. It is configured to run automatically during the `validate` phase (the very first phase), so the build fails fast if the code is messy.

```
<build>  
    <plugins>  
        <plugin>  
            <groupId>org.apache.maven.plugins</groupId>  
            <artifactId>maven-checkstyle-plugin</artifactId>  
            <version>3.3.1</version>  
            <!-- Adding the dependency explicitly allows you to use the latest Checkstyle feature-->  
            <dependencies>  
                <dependency>  
                    <groupId>com.puppycrawl.tools</groupId>  
                    <artifactId>checkstyle</artifactId>  
                    <version>10.12.5</version>  
                </dependency>  
            </dependencies>  
            <executions>  
                <execution>  
                    <id>validate</id>  
                    <phase>validate</phase>  
                    <goals>  
                        <goal>check</goal>  
                    </goals>  
                </execution>  
            </executions>  
            <configuration>  
                <!-- This tells the plugin which rules to enforce. -->  
                <!-- Built-in options: google_checks.xml or sun_checks.xml -->  
                <!-- You can point this to your own file as well -->  
                <configLocation>google_checks.xml</configLocation>  
                <!-- Without this, the plugin just says "Checkstyle failed" and hides the details in a file (target/checkstyle-result.xml).  -->  
                <!-- Setting this to true prints the specific line numbers and errors directly to your terminal.-->  
                <consoleOutput>true</consoleOutput>  
                <failsOnError>true</failsOnError>  
                <!-- This is the "Zero Tolerance" setting-->  
                <!-- For legacy projects, you might set this to false -->      
                <failOnViolation>true</failOnViolation>  
                  
                <includeTestSourceDirectory>false</includeTestSourceDirectory>  
            </configuration>  
        </plugin>  
    </plugins>  
</build>
```

You don’t always have to run a full build. You can trigger the check command directly:

```
mvn checkstyle:check
```

### The “Spring Boot” Special

If you work with Spring Boot, this is arguably the most important plugin you will use.

**spring-boot-maven-plugin**

- It repackages your standard JAR into an executable JAR with embedded Tomcat/Jetty.
- It allows you to run the application directly: `mvn spring-boot:run`.
- It generates build info (Git commit ID, build time) to be exposed via Actuator endpoints.

```
<build>  
    <plugins>  
        <plugin>  
            <groupId>org.springframework.boot</groupId>  
            <artifactId>spring-boot-maven-plugin</artifactId>  
            <version>3.2.1</version> <executions>  
                <execution>  
                    <id>repackage</id>  
                    <goals>  
                        <!-- This is the magic goal. -->  
                        <!-- It takes the standard JAR (produced by the maven-jar-plugin) and wraps it inside a Spring Boot loader structure  -->  
                        <goal>repackage</goal>  
                    </goals>  
                </execution>  
                <execution>  
                    <id>build-info</id>  
                    <goals>  
                        <!-- This generates a file at META-INF/build-info.properties -->  
                        <!-- If you have Spring Boot Actuator, hitting localhost:8080/actuator/info will show the build version and time automatically.  -->  
                        <goal>build-info</goal>  
                    </goals>  
                </execution>  
            </executions>  
              
            <configuration>  
                <mainClass>com.example.project.MyApplication</mainClass>                  
                <!-- Optimizes your artifact for Docker images (separating libraries from code for better caching) -->  
                <!-- this allows you to copy dependencies (which rarely change) into a separate layer from your application code (which changes often), significantly speeding up Docker builds.  -->  
                <layers>  
                    <enabled>true</enabled>  
                </layers>                  
                <excludes>  
                    <!-- Libraries like Lombok are only needed during compilation. They do not need to be in the final running JAR -->  
                    <exclude>  
                        <groupId>org.projectlombok</groupId>  
                        <artifactId>lombok</artifactId>  
                    </exclude>  
                </excludes>                  
                <classifier>exec</classifier>  
            </configuration>  
        </plugin>  
    </plugins>  
</build>
```

## Maven Settings (settings.xml)

While the `pom.xml` configures the **project** (what libraries it needs), the `settings.xml` configures the **environment** (where to find those libraries and how to log in).

==This separation is critical:== ==**Never put passwords or machine-specific paths in your**== ==`**pom.xml**`====. The POM is shared with the team; the Settings file stays on your machine.==

There are two locations for this file. Maven merges them, with the **User** file overriding the Global one.

- **User Settings (Recommended):  
    Location:** `${user.home}/.m2/settings.xml   `**Purpose:** Specific to your user. This is where you define your credentials and custom configurations.
- **Global Settings:  
    Location:** `${maven.home}/conf/settings.xml` (inside the Maven installation folder).  
    **Purpose:** Applies to all users on the machine. Usually used by System Admins on build servers (Jenkins/TeamCity).

Here is a comprehensive sample showing the most common configurations: custom storage location, proxy settings, repository credentials, and a corporate mirror.

```
<settings xmlns="http://maven.apache.org/SETTINGS/1.0.0"  
          xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"  
          xsi:schemaLocation="http://maven.apache.org/SETTINGS/1.0.0  
                              http://maven.apache.org/xsd/settings-1.0.0.xsd">  
  
  <localRepository>D:/maven/repo</localRepository>  
  
  <proxies>  
    <proxy>  
      <id>corporate-proxy</id>  
      <active>true</active>  
      <protocol>http</protocol>  
      <host>proxy.example.com</host>  
      <port>8080</port>  
      <nonProxyHosts>localhost|127.0.0.1|*.mycompany.com</nonProxyHosts>  
    </proxy>  
  </proxies>  
  
  <servers>  
    <server>  
      <id>my-corporate-nexus</id>  
      <username>jdoe</username>  
      <password>{COQLCE6DU6GtcS5P=}</password>  
    </server>  
  </servers>  
  
  <mirrors>  
    <mirror>  
      <id>my-corporate-nexus</id>  
      <name>Corporate Shared Repository</name>  
      <url>https://nexus.mycompany.com/repository/maven-public/</url>  
      <mirrorOf>*</mirrorOf>  
    </mirror>  
  </mirrors>  
  
  <profiles>  
    ==<====profile====>==      ======<====id====>====env-dev====</====id====>==      ======<====properties====>==        ======<====maven.compiler.source====>====17====</====maven.compiler.source====>==        ======<====maven.compiler.target====>====17====</====maven.compiler.target====>==      ======</====properties====>==    ======</====profile====>==  
  </profiles>  
  
  <activeProfiles>  
    <activeProfile>env-dev</activeProfile>  
  </activeProfiles>  
  
</settings>
```

**Key sections:**

```
<localRepository>
```

This controls where Maven stores downloaded JARs on your disk.  
**Why change it?** Developers often move this off their primary partition to save space or to place it on a faster SSD.

`<servers>` (The Vault)

This is the most important section for security. It maps a Repository ID (defined in your POM) to a username and password. The `<id>` here must match the `<id>` of the `<repository>` or `<distributionManagement>` element in your `pom.xml`.  
**Security Tip:** Never store plain text passwords. Use Maven’s built-in encryption and then paste the resulting encrypted string into the `<password>` tag.

```
mvn --encrypt-password "mypassword"
```

`<mirrors>` (The Traffic Cop)  
Mirrors are used to redirect traffic.

- **Usage:** If your company blocks direct access to the internet (Maven Central), you configure a mirror to say “When Maven asks for Central, go to `nexus.mycompany.com` instead."
- `**<mirrorOf>*</mirrorOf>**`: This is the "Nuclear Option." It tells Maven to look at your internal server for _everything_, ignoring all other repositories defined in POMs.

`<proxies>`

If your browser needs a proxy to access Google, Maven needs a proxy to access Central. This section configures standard HTTP/HTTPS tunneling.

`<profiles>` & `<activeProfiles>`

These are “Global Profiles.”

- Unlike profiles in a `pom.xml` (which only apply to that project), these apply to **every build you run on this machine**.
- **Common Use Case:** Setting a global property like the Java version or injecting a private repository URL that shouldn’t be hardcoded in project POMs.

The `settings.xml` is your personal configuration file. It bridges the gap between the public project definition (`pom.xml`) and your private local environment (passwords, file paths, and proxies).

## Testing With Maven

One of Maven’s greatest strengths is that it treats testing as a first-class citizen. Unlike older build tools where you had to manually script a “test” task, Maven bakes testing directly into its core lifecycle.

However, Maven makes a very important architectural distinction that often confuses beginners: the separation between **Unit Tests** (Surefire) and **Integration Tests** (Failsafe).

Maven believes these two types of tests have fundamentally different lifecycles and requirements.

- **Unit Tests:** Fast. Isolated. Run entirely in memory. If they fail, the build should stop immediately.
- **Integration Tests:** Slow. Complex. Require external resources (Database, Docker, Network). If they fail, we must still run a “teardown” phase to clean up the mess before stopping the build.

**Using Maven Surefire with Junit  
**The **Surefire** plugin is the default test runner. It runs during the `**test**` phase of the lifecycle.

By default, Surefire automatically finds and runs any class that follows these naming patterns in `src/test/java`:

- `**/Test*.java`
- `**/*Test.java`
- `**/*Tests.java`
- `**/*TestCase.java`

While Surefire works out of the box, you often need to configure it to handle ==modern Java versions or JUnit 5.==

```
<plugin>  
    <groupId>org.apache.maven.plugins</groupId>  
    <artifactId>maven-surefire-plugin</artifactId>  
    ==<====version====>====3.2.3====</====version====>==  
    <configuration>  
        <failIfNoTests>true</failIfNoTests>          
        <parallel>methods</parallel>  
        <threadCount>4</threadCount>  
    </configuration>  
</plugin>
```

Also, you need to add a dependency for Junit in pom.xml:

```
<dependency>  
        <groupId>org.junit.jupiter</groupId>  
        <artifactId>junit-jupiter</artifactId>  
        <version>5.10.1</version>  
        <scope>test</scope>  
</dependency>
```

To skip unit tests (e.g., during a hotfix deployment), use:

```
==mvn clean install -====DskipTests==
```

Note: This skips both Unit and Integration tests.

**Using Maven Surefire with TestNG  
**The `maven-surefire-plugin` is the default test runner in Maven. ==While it defaults to JUnit,== it has first-class support for TestNG.

First, you must include the TestNG library in your `pom.xml`.

```
<dependencies>  
    <dependency>  
        <groupId>org.testng</groupId>  
        <artifactId>testng</artifactId>  
        <version>7.9.0</version> <scope>test</scope>  
    </dependency>  
</dependencies>
```

If you name your test classes using standard conventions (e.g., `*Test.java`, `Test*.java`, `*TestCase.java`), Surefire will automatically detect and run them using TestNG without extra configuration.

However, it is best practice to define the plugin version explicitly

```
<build>  
    <plugins>  
        <plugin>  
            <groupId>org.apache.maven.plugins</groupId>  
            <artifactId>maven-surefire-plugin</artifactId>  
            <version>3.2.5</version>  
        </plugin>  
    </plugins>  
</build>
```

The real power of TestNG comes from using a `testng.xml` suite file to control execution order, parameters, and parallelism. You need to tell Surefire where this file is located.

```
<project>  
  ...  
  <build>  
    <plugins>  
      <plugin>  
        <groupId>org.apache.maven.plugins</groupId>  
        <artifactId>maven-surefire-plugin</artifactId>  
        <version>3.2.5</version>  
        <configuration>  
          <suiteXmlFiles>  
            <suiteXmlFile>src/test/resources/testng.xml</suiteXmlFile>  
          </suiteXmlFiles>  
        </configuration>  
      </plugin>  
    </plugins>  
  </build>  
  ...  
</project>
```

TestNG allows you to tag tests with groups (e.g., `@Test(groups = "regression")`). You can configure Surefire to run only specific groups directly from the `pom.xml` or via the command line.

in pom.xml:

```
<configuration>  
    <groups>regression</groups>  
    <excludedGroups>slow, integration</excludedGroups>  
</configuration>
```

**Via Command Line (Override):** You can run the build and pass the groups dynamically without changing the POM:

```
mvn test -Dgroups="smoke"
```

Surefire can delegate parallel execution to TestNG. This is useful for speeding up large test suites.

```
<configuration>  
    <suiteXmlFiles>  
        <suiteXmlFile>src/test/resources/testng.xml</suiteXmlFile>  
    </suiteXmlFiles>  
    <properties>  
        <property>  
            <name>parallel</name>  
            <value>methods</value>  
        </property>  
        <property>  
            <name>threadCount</name>  
            <value>4</value>  
        </property>  
    </properties>  
</configuration>
```

**Summary of Commands**

- `**mvn test**`: Runs the tests using the configuration in `pom.xml`.
- `**mvn test -Dtest=LoginTest**`: Runs a single test class (bypassing the suite XML).
- `**mvn test -Dgroups=smoke**`: Runs only the tests tagged with `@Test(groups="smoke")`.

**Running integration tests with Maven failsafe  
**The **Failsafe** plugin is designed for tests that require setup and teardown. It runs during the `**integration-test**` phase.

**Why a separate plugin?  
**If you used Surefire for integration tests and a test failed, Maven would halt the build immediately. If you had spun up a Docker container or a database in the `pre-integration-test` phase, it would be left running (a resource leak).

**Failsafe** solves this by continuing the build even if a test fails, allowing the `post-integration-test` phase to run and clean up resources, before finally reporting the failure in the `verify` phase.

By convention, Failsafe looks for these patterns:

- `**/IT*.java`
- `**/*IT.java`
- `**/*ITCase.java`

Unlike Surefire, Failsafe is **not** bound to the lifecycle by default. You must explicitly add the executions.

```
<plugin>  
    <groupId>org.apache.maven.plugins</groupId>  
    <artifactId>maven-failsafe-plugin</artifactId>  
    <version>3.2.3</version>  
    <executions>  
        <execution>  
            <goals>  
                <goal>integration-test</goal>  
                <goal>verify</goal>  
            </goals>  
        </execution>  
    </executions>  
</plugin>
```
	
**Code Coverage with Jacoco  
**Running tests is good; knowing how much code they cover is better. The **Jacoco** (Java Code Coverage) plugin integrates seamlessly with Surefire and Failsafe.

It attaches a runtime agent to your JVM during tests to record execution paths.

```
<plugin>  
    <groupId>org.jacoco</groupId>  
    <artifactId>jacoco-maven-plugin</artifactId>  
    <version>0.8.11</version>  
    <executions>  
        <execution>  
            <goals>  
                <goal>prepare-agent</goal>  
            </goals>  
        </execution>  
        <execution>  
            <id>report</id>  
            <phase>test</phase>  
            <goals>  
                <goal>report</goal>  
            </goals>  
        </execution>  
    </executions>  
</plugin>
```

Running `mvn test` will now generate a clickable HTML report in `target/site/jacoco/index.html`.

## Multi-module projects in Maven

A Maven **multi-module project** is a way to manage a large application by splitting it into smaller, connected sub-projects (modules) that are built and versioned together.

Instead of one massive `pom.xml` with thousands of lines, you have a **root project** (the parent) and several **sub-modules** (the children) that inherit configuration from the parent.

Imagine you are building an e-commerce application. Instead of putting everything in one bucket, you split it into logical layers.

```
my-ecommerce-app/             (Root / Aggregator)  
├── pom.xml                   (The Parent POM)  
├── core-service/             (Module 1: Backend Logic)  
│   ├── src/  
│   └── pom.xml  
├── web-api/                  (Module 2: REST Endpoints)  
│   ├── src/  
│   └── pom.xml  
└── shared-utils/             (Module 3: Common Utilities)  
    ├── src/  
    └── pom.xml
```

A multi-module project relies on two key Maven concepts working together: **Aggregation** and **Inheritance**.

### A. Aggregation (The “Builder”)

The Root POM acts as an **Aggregator**. It doesn’t contain code itself; it simply lists which modules belong to the project. When you run `mvn clean install` in the root, Maven's **Reactor** reads this list and builds every module in the correct order (e.g., building `shared-utils` before `core-service` because `core` depends on `utils`).

top level pom.xml example:

```
<project>  
    <groupId>com.example</groupId>  
    <artifactId>my-ecommerce-app</artifactId>  
    <version>1.0.0</version>  
      
    <packaging>pom</packaging>  
  
    <modules>  
        <module>shared-utils</module>  
        <module>core-service</module>  
        <module>web-api</module>  
    </modules>  
</project>
```

### B. Inheritance (The “Parent”)

The Root POM also acts as a **Parent**. It defines settings (Java version, dependency versions, plugins) that all children share. This keeps your child POMs clean and ensures consistency.

Child `pom.xml:`

```
<project>  
    <parent>  
        <groupId>com.example</groupId>  
        <artifactId>my-ecommerce-app</artifactId>  
        <version>1.0.0</version>  
    </parent>  
  
    <artifactId>core-service</artifactId>  
</project>
```

### The “Killer Feature”: Dependency Management

The most powerful reason to use this structure is `<dependencyManagement>`.

In a large team, you don’t want Module A using `Spring Boot 3.0` and Module B using `Spring Boot 2.5`.

- **In the Parent POM:** You define the _version_ of every library you might use in the `<dependencyManagement>` section.
- **In the Child POM:** You declare the dependency _without_ the version. Maven looks up to the parent to find the correct version.

parent POM:

```
<dependencyManagement>  
    <dependencies>  
        <dependency>  
            <groupId>org.springframework.boot</groupId>  
            <artifactId>spring-boot-starter-web</artifactId>  
            <version>3.1.2</version> </dependency>  
    </dependencies>  
</dependencyManagement>
```

Child POM:

```
<dependencies>  
    <dependency>  
        <groupId>org.springframework.boot</groupId>  
        <artifactId>spring-boot-starter-web</artifactId>  
    </dependency>  
</dependencies>
```

### Maven Flatten Plugin

The **Maven Flatten Plugin** is a tool used to clean up and simplify your `pom.xml` before it is deployed to a remote repository (like Nexus, Artifactory, or Maven Central).

Its primary job is to generate a new, stripped-down version of your POM (called the **flattened POM**) that replaces variables with literal values and removes build-specific configurations that consumers of your library don’t need.

**The Main Problem It Solves: “CI-Friendly Versions”  
**In modern DevOps, we often want to inject the version number dynamically during the build (e.g., `1.0.0-build-123`) rather than hardcoding it in the file.

If you set your version like this in a multi-module project:

```
<version>${revision}</version>
```

**Without the Flatten Plugin:** When you deploy this to a repository, the `pom.xml` uploaded still contains `${revision}`. When another developer tries to use your library, their Maven build will fail because it doesn't know what `${revision}` equals.

**With the Flatten Plugin:** It resolves `${revision}` to `1.0.0`, creates a new `.flattened-pom.xml` with that hardcoded number, and deploys _that_ file instead.

To use it, simply add the plugin to your **Root Parent POM** in the `<build>` section.

```
<build>  
    <plugins>  
        <plugin>  
            <groupId>org.codehaus.mojo</groupId>  
            <artifactId>flatten-maven-plugin</artifactId>  
            <version>1.6.0</version> <configuration>  
                <updatePomFile>true</updatePomFile>                  
                <flattenMode>resolveCiFriendliesOnly</flattenMode>  
            </configuration>  
            <executions>  
                <execution>  
                    <id>flatten</id>  
                    <phase>process-resources</phase>  
                    <goals>  
                        <goal>flatten</goal>  
                    </goals>  
                </execution>  
                <execution>  
                    <id>flatten.clean</id>  
                    <phase>clean</phase>  
                    <goals>  
                        <goal>clean</goal>  
                    </goals>  
                </execution>  
            </executions>  
        </plugin>  
    </plugins>  
</build>
```

Let's look at the flattenMode:  
1. resolveCiFriendliesOnly: Only replaces `${revision}`, `${sha1}`, and `${changelist}`. Keeps everything else intact. Best for internal enterprise projects  
2. oss: Keeps standard metadata (licenses, developers, scm) but strips build configuration.  
3. bom:  
4. defaults: Removes name, description, url, etc. Best fit for genera; purpose libraries

## Deploying Apache Maven Projects to Nexus

Deploying artifacts to Nexus requires a “handshake” between two files: your project’s `**pom.xml**` (which says _where_ to send the files) and your local `**settings.xml**` (which holds the _keys/credentials_ to get in).

### 1. The “Where”: Configure `pom.xml`

You must tell Maven the URL of your Nexus repositories. You typically have two targets: one for **Snapshots** (development builds) and one for **Releases** (stable, final builds).

Add this `<distributionManagement>` section to your root `pom.xml`:

```
<project>  
    ...  
    <distributionManagement>  
        <repository>  
            <id>nexus-releases</id>  
            <name>Nexus Release Repository</name>  
            <url>http://your-nexus-domain.com/repository/maven-releases/</url>  
        </repository>  
        <snapshotRepository>  
            <id>nexus-snapshots</id>  
            <name>Nexus Snapshot Repository</name>  
            <url>http://your-nexus-domain.com/repository/maven-snapshots/</url>  
        </snapshotRepository>  
    </distributionManagement>  
    ...  
</project>
```

**Note:** Maven automatically picks the correct URL. If your version ends in `-SNAPSHOT` (e.g., `1.0-SNAPSHOT`), it uses `snapshotRepository`. If it doesn't (e.g., `1.0`), it uses `repository`.

### 2. The “Key”: Configure `settings.xml`

For security, you **never** put passwords in the `pom.xml`. Instead, they go in your global Maven settings file, typically found at `~/.m2/settings.xml` (or `%USERPROFILE%\.m2\settings.xml` on Windows).

**Crucial Rule:** The `<id>` in `settings.xml` **must match exactly** the `<id>` you used in `pom.xml`.

```
<settings>  
    ...  
    <servers>  
        <server>  
            <id>nexus-releases</id>   
            <username>admin</username>  
            <password>admin123</password>  
        </server>  
        <server>  
            <id>nexus-snapshots</id>   
            <username>admin</username>  
            <password>admin123</password>  
        </server>  
    </servers>  
    ...  
</settings>
```

Once the configuration is in place, deploying is a single command. Run this from your project root:

```
mvn deploy
```

### **What happens next?**

1. **Validate/Compile/Test:** Maven runs the standard build lifecycle.
2. **Package:** It creates your JAR/WAR file.
3. **Upload:** The `maven-deploy-plugin` activates. It checks your project version:

- Is it `1.0.0-SNAPSHOT`? → It looks for `<snapshotRepository>` in POM → Looks for matching ID in `settings.xml` → Uploads to the Snapshot URL.
- Is it `1.0.0`? → It looks for `<repository>` in POM → Looks for matching ID → Uploads to the Release URL.

### Pro Tip: Using Environment Variables for CI/CD

If you are deploying from Jenkins or GitHub Actions, do not hardcode passwords in `settings.xml`. Use environment variables instead:

```
<server>  
    <id>nexus-releases</id>  
    <username>${env.NEXUS_USERNAME}</username>  
    <password>${env.NEXUS_PASSWORD}</password>  
</server>
```

## Maven Build profiles

==**Maven Build Profiles**== ==allow you to dynamically modify your build configuration based on the environment you are building for.==

Instead of changing your code or `pom.xml` manually every time you switch from development to production, you just activate the correct profile

Example: Different Databases for Dev vs. Prod

In your `pom.xml`:

```
<project>  
    ...  
    <properties>  
        <env>default</env>  
    </properties>  
  
    <profiles>  
        <profile>  
            <id>dev</id>  
            <activation>  
                <activeByDefault>true</activeByDefault> </activation>  
            <properties>  
                <db.url>jdbc:h2:mem:testdb</db.url>   
                <db.user>sa</db.user>  
                <app.mode>DEBUG</app.mode>  
            </properties>  
        </profile>  
  
        <profile>  
            <id>prod</id>  
            <properties>  
                <db.url>jdbc:postgresql://prod-db-server:5432/orders</db.url>  
                <db.user>admin_secure</db.user>  
                <app.mode>RELEASE</app.mode>  
            </properties>  
        </profile>  
    </profiles>  
    ...  
</project>
```

To activate a specific profile, use the `-P` flag followed by the profile ID.

To run the Dev profile (default): Since we set `<activeByDefault>true</activeByDefault>` for `dev`, it runs automatically.

```
mvn clean install
```

To run the Production profile:

```
mvn clean install -Pprod
```

This forces Maven to ignore the `dev` properties and use the `prod` properties instead.

Example: Changing Build Behavior  
Profiles aren’t just for variables; they can change **what** gets built.

Imagine you have very slow integration tests that take 20 minutes. You don’t want to run them every time you save a file. You can put them in a separate profile.

==A “Quick Build” Profile:==

```
<profiles>  
    <profile>  
        <id>quick-build</id>  
        <properties>  
            <maven.test.skip>true</maven.test.skip>  
            <maven.javadoc.skip>true</maven.javadoc.skip>  
        </properties>  
    </profile>  
</profiles>
```

Usage:

```
# Regular build (runs all tests)  
mvn clean install  
  
# "I'm in a hurry" build (skips tests and docs)  
mvn clean install -Pquick-build
```

Besides using `-P`, you can also trigger profiles automatically based on environmental conditions:

- OS-based: Activates when running on a specific OS. _<os><family>windows</family></os>_
- JDK-based: Activates if running a specific Java version. _<jdk>11</jdk>_
- File: Activates if a specific file exists. _<file><exists>./local-config.xml</exists></file>_

## Maven release plugin

The **Maven Release Plugin** is the automation tool that manages the lifecycle of releasing a software version.

Manually releasing software is error-prone: you might forget to update a version number, mistype a Git tag, or forget to deploy the artifacts. The Release Plugin automates this entire “Release Dance” into two standardized goals: **Prepare** and **Perform**.

For example, lets say, you are ready to build and ship version 1.0.0 of your project

### Step A: `mvn release:prepare`

This goal interacts with your version control (Git) and your POM files.

1. **Check:** Verifies there are no uncommitted changes in your workspace.
2. **Strip Snapshot:** Changes version from `1.0.0-SNAPSHOT` to `1.0.0` in all POMs.
3. **Tag:** Commits this change and creates a Git Tag (e.g., `v1.0.0`).
4. **Bump:** Changes the version to the _next_ development version (e.g., `1.0.1-SNAPSHOT`).
5. **Commit:** Commits the new snapshot version to the main branch.

### Step B: `mvn release:perform`

This goal interacts with the build and your artifact repository (Nexus/Artifactory).

1. **Checkout:** It checks out the code from the Git Tag created in Step A (to ensure a clean build).
2. **Build & Deploy:** It runs `mvn deploy` on that checked-out code, compiling the artifacts and uploading them to your "Releases" repository.

To use this plugin, you **must** configure the `<scm>` (Source Control Management) section so Maven knows where your Git repository is.

```
<project>  
    ...  
    <scm>  
        <connection>scm:git:git://github.com/myuser/my-app.git</connection>  
        <developerConnection>scm:git:ssh://github.com:myuser/my-app.git</developerConnection>  
        <url>http://github.com/myuser/my-app</url>  
        <tag>HEAD</tag>  
    </scm>  
  
    <build>  
        <plugins>  
            <plugin>  
                <groupId>org.apache.maven.plugins</groupId>  
                <artifactId>maven-release-plugin</artifactId>  
                <version>3.0.1</version>  
                <configuration>  
                    <autoVersionSubmodules>true</autoVersionSubmodules>                      
                    <tagNameFormat>v@{project.version}</tagNameFormat>   
                    <pushChanges>false</pushChanges>  
                </configuration>  
            </plugin>  
        </plugins>  
    </build>  
    ...  
</project>
```

Assuming you have configured your `distributionManagement` (for Nexus) and `scm` (for Git), you run:

```
# 1. Prepare the release  
# It will interactively ask you:  
# - What is the release version? (Defaults to 1.0.0)  
# - What is the SCM release tag? (Defaults to v1.0.0)  
# - What is the new development version? (Defaults to 1.0.1-SNAPSHOT)  
mvn release:prepare  
  
# 2. Perform the release  
# This uploads the artifacts to Nexus  
mvn release:perform
```

To run it non-interactively (good for CI/CD servers): (The `-B` flag stands for Batch mode, suppressing prompts)

```
mvn release:prepare -DreleaseVersion=1.0.0 -DdevelopmentVersion=1.1.0-SNAPSHOT -Dtag=v1.0.0 -B
```

Maven does not have a built-in “login screen” for Git (or whatever version control software you are using). Instead, it relies on one of two methods: it either **delegates** authentication to your operating system’s Git configuration (most common), or it reads credentials from your `**settings.xml**` (explicit configuration).

### Method 1: System Delegation (SSH Keys) — The Standard Way

In 90% of cases, Maven doesn’t handle the password at all. It simply runs the `git` command, and your underlying Git setup handles the handshake.

If your `<scm>` connection URL looks like this: _<connection>scm:git:git@github.com:myuser/my-app.git</connection> ,_ Maven sees the `git@...` and knows to use the **SSH protocol.** Maven invokes the native Git client and Git looks for your private SSH key in `~/.ssh/id_rsa` (Linux/Mac) or `%USERPROFILE%\.ssh\id_rsa` (Windows). If the key is loaded in your **SSH Agent**, the commit happens without asking for a password.

If your Jenkins/GitHub Actions runner doesn’t have the SSH private key loaded, Maven will hang waiting for a passphrase or fail with `Auth fail`.

### Method 2: Maven Settings (HTTPS/Tokens) — _The Explicit Way_

If you are using **HTTPS** URLs (common in corporate environments or when using Personal Access Tokens), you can store credentials in your `settings.xml`.

1. **The** `**pom.xml**` **Setup** You must tell the SCM plugin _which_ set of credentials to use. You do this by adding a special property `project.scm.id`.

```
<properties>  
    <project.scm.id>github-server</project.scm.id>  
</properties>  
  
<scm>  
    <connection>scm:git:https://github.com/myuser/my-app.git</connection>  
    <developerConnection>scm:git:https://github.com/myuser/my-app.git</developerConnection>  
</scm>
```

2. **The** `**settings.xml**` **Setup:** In your `~/.m2/settings.xml`, create a `<server>` entry with an ID that matches the property above

```
<servers>  
    <server>  
        <id>github-server</id> <username>myuser</username>  
        <password>ghp_SECRET_TOKEN_HERE</password>  
    </server>  
</servers>
```

### Method 3: CI/CD Injection (The DevOps Way)

In modern pipelines (GitLab CI, GitHub Actions), you often don’t touch `settings.xml` for SCM.

Instead, the CI pipeline checks out the code using a special token before Maven even starts.

- **GitHub Actions:** Automatically injects the `GITHUB_TOKEN` into the local git config.
- **Jenkins:** often uses the “SSH Agent” plugin to inject the key into the session.

Maven just runs `git push`, and because the environment is already authenticated by the pipeline runner, it succeeds.

### Common Issues & Tips

- `**release.properties**` **file:** When `release:prepare` runs, it creates a `release.properties` file to store the state. If the command fails halfway, **you must delete this file** (and usually run `mvn release:clean`) before trying again.
- **Git Credentials:** The environment running the build must have SSH keys or credentials set up for Git, or `release:prepare` will fail when trying to push the tag.
- **Test Failures:** `release:prepare` runs your unit tests by default. If tests fail, the release is aborted. To skip them (risky, but common), use `-Darguments="-Dmaven.test.skip=true"`.

When the Maven Release Plugin runs, it sees `project.scm.id`, looks up `github-server` in your settings, and passes that username/token to the underlying Git command during the push.

## Maven Bill of Materials (BOM)

A **Maven Bill of Materials (BOM)** is a special kind of POM file that groups a set of related dependencies and guarantees that they work together at specific versions

Think of it as a **“Curated Catalog”** or a **“Menu”** of compatible library versions. Instead of every developer on your team guessing which version of `library-A` works with `library-B`, the BOM defines the "golden standard" for the entire organization.

Without a BOM, you might have:

- Project A using `Spring Framework 5.0`
- Project B using `Spring Framework 5.3`
- Project C using `Jackson JSON 2.9` (which crashes with Spring 5.3)

This leads to “Dependency Hell” where libraries conflict and the application fails at runtime.

### The Solution: The BOM File

A BOM is simply a `pom.xml` file that contains **only** a `<dependencyManagement>` section. It lists the versions, but it does not actually add the JARs to your project—it just defines them.

the project declaring BOM:

```
<project>  
    <groupId>com.mycompany</groupId>  
    <artifactId>my-company-bom</artifactId>  
    <version>1.0.0</version>  
    <packaging>pom</packaging> <dependencyManagement>  
        <dependencies>  
            <dependency>  
                <groupId>com.fasterxml.jackson.core</groupId>  
                <artifactId>jackson-databind</artifactId>  
                <version>2.15.2</version>  
            </dependency>  
            <dependency>  
                <groupId>com.google.code.gson</groupId>  
                <artifactId>gson</artifactId>  
                <version>2.10.1</version>  
            </dependency>  
        </dependencies>  
    </dependencyManagement>  
</project>
```

To use the BOM, you don’t use `<parent>`. Instead, you **import** it in your project's `<dependencyManagement>` section. This is powerful because **you can import multiple BOMs** (e.g., one for Spring, one for AWS SDK, one for Internal Utils), whereas you can only have one Parent.

The project using BOM:

```
<dependencyManagement>  
    <dependencies>  
        <dependency>  
            <groupId>com.mycompany</groupId>  
            <artifactId>my-company-bom</artifactId>  
            <version>1.0.0</version>  
            <type>pom</type>  
            <scope>import</scope>   
        </dependency>  
    </dependencies>  
</dependencyManagement>  
  
<dependencies>  
    <dependency>  
        <groupId>com.fasterxml.jackson.core</groupId>  
        <artifactId>jackson-databind</artifactId>  
    </dependency>  
</dependencies>
```

The most famous BOM is `spring-boot-dependencies`. When you use Spring Boot, you don't manually pick the version for `hibernate`, `tomcat`, `jackson`, or `logback`. You just import the Spring Boot BOM, and it provides a list of ~200 libraries that are tested and guaranteed to work together.
